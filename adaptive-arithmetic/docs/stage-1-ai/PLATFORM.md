# Complete local Stage 1 platform

The user's comprehensive completion request is recorded in D-017. [FEATURE_GAPS.md](FEATURE_GAPS.md) is the stable F01–F27 acceptance matrix; this document resolves and records its implementation defaults. Full human acceptance remains separate from passing verification. Stage 2 learning is excluded.

## Practice entry and content

The default screen is **Standard Zetamac**, with one-click **Start standard run**: 120 seconds, immediate start, equal four-operation selection and independent inclusive integer samples. Addition uses a,b from 2–100; subtraction displays (a+b)−a and expects b. Multiplication uses a from 2–12 and b from 2–100; division displays (a×b)÷a and expects b. Repeats are permitted. Original source/rules and verification hash are retained in the screening matrix.

Standard uses mode `standard`, content `zetamac-default-v1`, generator `zetamac-reverse-v1`, and policy `equal-operations-v1`. Its complete fixed config is stored with each run and enforced by the API. It is fixed/nonadaptive. Our monotonic render clock, exclusive deadline, focus-loss ending and exact numeric equivalence deliberately differ from the original game's runtime; the visible rules disclosure explains that scores are not externally interchangeable.

**Custom practice** keeps its approved full editor and independently remembered valid setup. Mode `custom`, content `custom-grid-v1`, generator `exact-grid-v1` and policy `hierarchical-shares-v1` identify new custom runs. Loaded read-only views do not write last setup; valid user edits continue saving across navigation. Existing version/config/seed custom output and random consumption are preserved, verified against a digest captured from committed pre-completion source.

Initial setup reads apply remembered values only before a deliberate Custom edit. Delayed/duplicate StrictMode reads and in-place connection retries cannot discard newer group/range/session edits; valid edits become the remembered setup after initialization succeeds.

`SelectionPolicy.choose(config, random)` is the replaceable fixed-standard/weighted-random boundary. Uniform exact operand generation and session execution remain independent. No model, adaptation, training framework or learning recommendation is included.

### Optiver 80 in 8 (D-031)

The separate **Optiver 80 in 8** entry provides 80 sequential four-choice questions in eight minutes, including integers, decimals, fractions/mixed numbers and missing operands. Correct choices earn +1, incorrect choices −1, and unanswered questions zero. A fresh seeded paper follows the observed public QuantPrep trial's question-family profile. The 56-point practice target and content-fidelity limits are disclosed; official question-bank/cutoff equivalence is unverified.

Optiver continues through focus loss and completes after all 80 submissions or a valid eight-minute timeout. Its immutable `answer-submitted` events and `choice-response-v1` measurements support separate net-score/accuracy/pass-rate/timing/pace analytics and exact four-choice review. Standard/Custom typed-input behavior is unchanged. [OPTIVER.md](OPTIVER.md) is authoritative for its generator/provenance, completion eligibility, recovery, analytics and export semantics; the fixed profile does not claim weighted operation/group selection probabilities.

## Results, history and comparisons

For Standard and Custom, score is recorded accepted-question count. Full-run comparison eligibility requires a known observed end, normal timeout at the complete configured duration, start at elapsed zero, at least one presented question, current mode/content/measurement provenance and no inconsistent trace. A real full zero-score run is eligible and has null timing aggregates. Manual/focus/recovery/untimed runs display partial counts. Invalid arithmetic, input, precision, ranges, subtraction constraints, selection shares/pair counts or standard rules retain raw records and warnings but contribute no valid derived timing for the affected question. Optiver instead uses correct-minus-incorrect net points, permits valid early completion after all 80 choices, and retains incorrect-choice response times under its separate contract.

All timing, questions and metrics come from the existing backend `derive_session`, which dispatches Optiver to its mode-specific derivation; the browser formats or plots supplied values. First-input is separate from correct-answer time; zero is valid, missing is null, and unfinished duration remains a lower bound when the end is unknown. Typed-answer edits do not establish wrong attempts or accuracy. Optiver accuracy uses explicit choice submissions; no mode claims pure calculation speed.

History defaults to eligible full runs, newest first, with stable creation-time/identity ordering, 20-row pages, standard/custom/optiver/legacy mode, state, inclusive UTC date and original-config text filters. The unchecked **Show non-eligible runs** checkbox opts into all matching records, including ongoing/interrupted/endless/legacy/inconsistent runs. Eligibility filtering precedes total/pagination calculation; changing the checkbox resets page one. An empty eligible selection explains how to inspect excluded sessions. Direct detail access, exports and closed-history deletion remain available independently of the listing filter. Refresh/retry/back navigation and downloads are available. Ongoing and unknown-end records are explicit.

When a refreshed matching total shrinks past the current page, History fetches the last existing page before displaying rows/range. A zero total resets to the initial page and shows zero sessions; active filters remain selected.

Each comparison key hashes canonical JSON of the full original configuration plus mode/content/generator/policy/measurement versions. Names and group IDs deliberately remain part of identity; rename-only configurations are conservatively separate. ## Reload during practice

Reloading during Standard, Optiver, Custom timed/endless, or countdown practice immediately creates one new session with a fresh identity and random seed. The prior mode, content and duration are retained; countdown is false in the replacement's immutable snapshot. Remembered Custom settings are not rewritten, so a prior countdown-enabled run and its replacement can belong to different conservative configuration cohorts.

An origin/tab-scoped sessionStorage marker records version, session identity, mode and configuration. Only actual reload navigation on a practice view consumes it; normal navigation and History/Graphs entry discard it. A quick nonblocking check of the prior session's Web Lock rejects copied markers while another tab still owns that run. Recovery is scheduled after that check so it cannot take the prior-owner lock first. Start bypasses asynchronous setup loading and does not await unrelated journal recovery. Creation/ownership still must succeed before question presentation; failed starts show an explicit retry. StrictMode consumes intent once and a synchronous start guard prevents duplicate requests.

The previous run ends through existing unload observation persistence or ownership-aware immutable-prefix recovery. It remains inspectable and excluded from full-run comparisons. Blur/hidden/pagehide sequences retain the restart candidate to support toolbar reloads; timeout/manual end, returning focus to ended results, results interaction or leaving results clears it. Recovery errors/journals survive and have an accessible retry during the replacement run. Mode-specific focus-loss and timed-deadline rules apply to each new run; Optiver continues through focus loss. Storage failures explicitly report restart unavailability; the established journal/unacknowledged-exit preservation limit remains.

## Retention, deletion and concurrency

Sessions are **kept locally until explicitly deleted**. One closed session or an exact preview of all closed history can be deleted only after destructive confirmation. Server transactions recheck all IDs and delete observations plus sessions atomically; conflicts are nonmutating. New records arriving after confirmation are not silently included. Presets and remembered configuration are untouched.

D-026 labels global deletion **Delete all closed runs, including hidden runs**. A separate **Delete matching runs** uses all current History filters, including eligibility, across every matching page; its preview omits pagination parameters and the confirmation names that scope. Hidden/nonmatching records and arrivals after the preview remain outside it. Both paths retain the existing per-session browser ownership/pending-journal checks and exact-ID atomic server recheck. Empty/invalid matching selections disable the filtered action; the global action remains explicitly separate.

Database-open or missing-terminal rows are protected. The browser additionally checks recovery journals and acquires each session's Web Lock, protecting owned/queued data; it never removes journals as part of deletion. Bulk confirmation reports its actual selected count plus protected ongoing/owned/pending count. The entire exact confirmed scope is supported without an arbitrary session-count cap; a 10,001-record deletion/protection regression passes. Failures leave records intact, offer retry and refresh history/graphs/export after success. Tests only delete synthetic databases.

Session reads, list, analytics and exports use one explicit SQLite read transaction and have no recovery/end side effects. WAL allows complete before/after snapshots through concurrent appends/deletes. Fresh history/graph entry neither recovers abandoned journals nor autosaves loaded controls; entering a practice screen enables normal ownership-aware recovery. No third-party telemetry/cloud storage exists. Browser locks/journals are origin-scoped; use the canonical local URL. The existing combined journal-failure/unacknowledged-exit limit remains.

## API additions

`POST /api/sessions` accepts an optional bounded opaque `creationKey`. A nullable SQLite `creation_key` column and unique partial index make repeated requests with the same key/config/seed/versions return the same retained session ID atomically. A valid but different payload under that key returns 409 without changing the original. Legacy requests without a key retain their prior create semantics. Raw historical configurations/events/metadata are not rewritten, and measurement/content/generator/policy versions stay unchanged.

The browser journals the entire creation request under `arithmetic.creating.<creationKey>` before POST and owns a separate Web Lock through an unresolved/failed attempt. Retry retains that request and seed. Successful creation installs an empty observation journal under session ownership before retiring the creation marker; a document lost before first presentation is recoverable. On practice entry, abandoned creation markers are reconciled through the idempotent endpoint and then ordinary immutable-prefix recovery; live owners and read-only History/Graphs are not recovered. Malformed/failed markers remain inspectable with retry errors. Lock release returns confirmation from the browser; recovery waits for its creation-to-observation handoff so the next lock acquisition cannot incorrectly skip a just-released record. Creation keys last only with their retained session; deletion does not keep an additional tombstone history.

| Endpoint | Meaning |
| --- | --- |
| `GET /api/sessions?offset=&limit=&mode=&status=&after=&before=&configuration=&eligibleOnly=` | Snapshot-consistent history summaries, total, paging and snapshot time; `eligibleOnly` defaults false for API compatibility, while History explicitly sends true by default |
| `GET /api/analytics?cohort=&includePartial=&after=&before=` | Backend cohort choices, eligible chronology, histogram, breakdown, counts/reasons and session selection |
| `GET /api/sessions/deletion-preview?mode=&status=&after=&before=&configuration=&eligibleOnly=` | Exact matching closed IDs across all pages, count, protected count and snapshot time; omitted filters preserve global preview semantics |
| `DELETE /api/sessions` with `{sessionIds:[...]}` | Atomic deletion of the exact confirmed closed scope |
| `DELETE /api/sessions/{id}` | Atomic closed-only single deletion |

Existing reads/JSON exports additionally include nullable mode/content, score/state/eligibility, cohort identity and per-session analysis. CSV adds camelCase mode/content/cohort/score/eligibility columns while preserving exact arithmetic and JSON raw-input encoding. SQLite adds nullable `mode` and `content_version`; historical configurations, metadata and events are never relabelled or rewritten.
